# linux-admin-toolkit

Набор скриптов для повседневных задач системного администрирования: резервное копирование, проверка доступности узлов, разбор логов и снятие состояния сервера.

Скрипты написаны под реальные задачи, а не как учебные примеры: у каждого есть обработка ошибок, коды возврата для запуска из cron и понятный вывод.

## Состав

| Скрипт | Назначение | Язык |
|---|---|---|
| `scripts/backup.sh` | Резервное копирование каталога с ротацией и проверкой целостности архива | Bash |
| `scripts/host_check.py` | Параллельная проверка доступности узлов по ICMP и TCP-портам | Python 3 |
| `scripts/log_report.py` | Сводка по логам: группировка ошибок, топ источников, поиск всплесков | Python 3 |
| `scripts/sysinfo.sh` | Снимок состояния сервера: CPU, память, диски, сервисы, сеть | Bash |

Внешних зависимостей нет — только стандартная библиотека Python и штатные утилиты Linux.

## Требования

- Linux (протестировано на Ubuntu 24.04)
- Python 3.10+ (используются аннотации типов вида `float | None`)
- Bash 4.0+
- Для ICMP-проверок: пакет `iputils-ping`. Без него `host_check.py` не падает, а честно помечает ICMP как недоступный и судит о состоянии узла по портам.

## Установка

```bash
git clone https://github.com/AlterVoltrix/linux-admin-toolkit.git
cd linux-admin-toolkit
chmod +x scripts/*.sh scripts/*.py
```

## Использование

### backup.sh — бэкап с ротацией

```bash
./scripts/backup.sh -s /var/www -d /backup -k 7
```

| Ключ | Значение |
|---|---|
| `-s` | каталог-источник |
| `-d` | каталог для архивов |
| `-k` | сколько последних архивов хранить (по умолчанию 7) |

Что делает помимо самого архивирования:

- перед началом проверяет, хватает ли свободного места
- проверяет целостность созданного архива (`tar -tzf`) и удаляет его, если он битый — незамеченный повреждённый бэкап хуже, чем его отсутствие
- пишет в stdout и в syslog, поэтому запуск из cron не остаётся без следов
- ротация идёт по имени файла: временная метка в имени делает сортировку по имени хронологической

Пример записи в cron — ежедневно в 3:15:

```
15 3 * * * /opt/linux-admin-toolkit/scripts/backup.sh -s /var/www -d /backup -k 14
```

### host_check.py — проверка доступности

```bash
./scripts/host_check.py -f hosts.json            # полный отчёт
./scripts/host_check.py -f hosts.json --quiet    # только проблемные узлы
./scripts/host_check.py -f hosts.json --json     # машиночитаемый вывод
```

Формат `hosts.json`:

```json
{
  "switch-01": {"host": "10.0.0.11", "ports": [22, 80]},
  "tftp":      {"host": "10.0.0.5",  "ports": [69]},
  "db":        {"host": "10.0.0.20", "ports": [3306]}
}
```

Особенности:

- проверки идут параллельно (`ThreadPoolExecutor`) — 50 узлов проверяются за секунды, а не за минуты
- ICMP и TCP проверяются независимо: ICMP часто закрыт файрволом, но сервис при этом жив
- код возврата 1 при наличии проблем — можно вешать на cron или подключать как внешнюю проверку в Zabbix

### log_report.py — сводка по логам

```bash
./scripts/log_report.py /var/log/syslog
./scripts/log_report.py /var/log/syslog --level ERROR --top 20
journalctl -n 5000 --no-pager | ./scripts/log_report.py -
./scripts/log_report.py /var/log/nginx/error.log --pattern timeout
```

Ключевая идея — нормализация сообщений перед подсчётом. Строки

```
ERROR upstream timed out while connecting to 10.0.0.4:8080
ERROR upstream timed out while connecting to 10.0.0.7:8080
```

сводятся к одному шаблону `ERROR upstream timed out while connecting to <IP>:<N>` и считаются как одна ошибка, повторившаяся дважды. Без этого счётчик показывает тысячу «уникальных» ошибок вместо одной проблемы.

Пример вывода:

```
Распределение по уровням:
  INFO             4   44.4%  ######################
  ERROR            3   33.3%  ################
  WARNING          1   11.1%  #####
  CRITICAL         1   11.1%  #####

Топ-5 повторяющихся ошибок:
  [    3x] ERROR upstream timed out while connecting to <IP>:<N>
  [    1x] CRITICAL Disk full on <PATH>
```

Поддерживаются формат syslog и ISO-формат; строки нестандартного вида не теряются, а попадают в группу `unparsed`.

### sysinfo.sh — состояние сервера

```bash
./scripts/sysinfo.sh           # полный отчёт
./scripts/sysinfo.sh --check   # только проблемы, код возврата 1 если что-то не так
./scripts/sysinfo.sh --json    # для мониторинга
```

Проверяет и отмечает как проблему:

- load average выше удвоенного числа ядер
- занятость памяти выше 90%
- использование swap выше 50% — на сервере это почти всегда признак нехватки памяти
- заполнение дисков выше 85%
- **исчерпание inode** — место на диске есть, а файл создать нельзя; частая и неочевидная причина инцидентов
- упавшие юниты systemd
- недоступность шлюза по умолчанию

Пороги вынесены в переменные в начале файла.

## Заметки по реализации

Несколько решений, которые стоит пояснить:

**Почему `set -euo pipefail` в `backup.sh`, но без `-e` в `sysinfo.sh`.** Бэкап должен останавливаться на первой ошибке — частично выполненное копирование опаснее, чем невыполненное. Сбор диагностики, наоборот, должен доработать до конца даже на минимальной системе, где половина утилит отсутствует.

**Почему потоки, а не asyncio, в `host_check.py`.** Проверки почти всё время ждут ответа сети, GIL здесь не мешает, а `ThreadPoolExecutor` даёт то же ускорение при заметно более простом коде.

**Почему `subprocess` вместо raw-сокетов для ICMP.** Raw-сокеты требуют root. Системный `ping` имеет suid и работает от обычного пользователя — скрипт не нужно запускать с повышенными правами.

**Проверка наличия утилит.** Скрипты не предполагают, что `ping`, `ip` или `ss` установлены. Если утилиты нет, это отражается в выводе явно, а не превращается в ложную тревогу по всем узлам сразу.
